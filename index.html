design-aidlc 指令表

設計師大多不用打指令，直接用中文跟 agent 說要做什麼，它會自己跑對的指令。這份表是讓你知道「有哪些、什麼時候用」，需要時按「複製」貼給 agent。

最常用的只有 4 個：/design-aidlc 開始設計 · /design-aidlc move 搬檔 · /design-aidlc finish 檢查 · /design-aidlc-update 更新專案

日常流程

檔案依成熟度走三個區域：草稿 → 定稿協作 → 交付。搬檔是「複製」，不會改內容。

草稿workspace/designs/<你的資料夾>/<platform>/自己的作品，給 PM 看、修改
定稿協作workspace/co-work/<platform>/與視覺、UX writer 精修
交付<platform>/handoff/確認要給工程的檔案

三個區域的結構一樣：views/、demo/、css/、js/、assets/、strings.*.json。草稿和 co-work 的頁面可直接用瀏覽器打開，搬檔時路徑不用改。

  1. 開始設計直接說要做什麼，agent 會問平台與輸出區域。 
    把這個 Figma 連結做成設計 <Figma URL>
  2. 草稿 → 定稿協作PM 同意後搬過去，之後只改 co-work 的檔案。 
    /design-aidlc move draft-to-cowork login.html settings.html
  3. 定稿協作 → 交付精修完成後搬進 handoff。畫面用到的 css / js / 圖片會一起帶過去；strings.*.json 不會搬，搬完要確認 views 用到的 key 在交付區的文案檔都有，並跑 map 和 log --kind handoff。 
    /design-aidlc move cowork-to-delivery login.html settings.html
  4. 做完檢查修掉 findings。finish 與 handoff 只看交付區。 
    /design-aidlc finish
  5. 交給工程前從工程角度再讀一次，處理 BLOCK / GUESS / DRIFT。 
    /design-aidlc handoff web
  6. commit / 開 PR你說了才做，agent 會先問。

三種開始方式

依你手上有什麼來選。三種做完都一樣：畫面（views）、串起來的 demo、說明 md，之後 agent 會再補缺的狀態和沒去處的按鈕。

A：已經有 Figma 或畫面圖

適合：Figma wireframe，或 PNG / JPG 畫面截圖。agent 會把它做成可以點的 HTML。

/design-aidlc 把這個 Figma 連結做成設計 <Figma URL>，平台 app，放草稿。
/design-aidlc 把這幾張圖做成一個流程，圖片在 <圖片資料夾路徑>，平台 app，放草稿。

你會被問：圖片的順序（圖片沒有連結，agent 會先提議順序給你確認）、看不出來的狀態和按鈕行為。圖片只當參考，不會放進交付。

B：只有需求或一段描述

適合：需求 md、一段文字，或只知道「誰要做什麼」。agent 會先列出可能的流程給你挑，不會直接做。

/design-aidlc 使用者是<誰>，想要<做什麼>。請先列出需要的流程，我選了再做。
/design-aidlc 根據這份需求 <需求 md 路徑>，先列出需要的流程，我選了再做。

你會被問：選哪幾個流程（最多 4 個）、需求沒寫到的地方。還沒決定的事會記在 demo 的 .decision.md，不會混進正式說明。

C：已經有一組做好的 HTML，照它做新功能

適合：「照 Call Block 的畫面，做 Web Guard」這種。一次一個功能。agent 會先比對再停下來，等你決定才開始做。

/design-aidlc 照 <範例畫面資料夾> 的畫面，做 <新功能名稱>，規格在 <規格檔路徑>。先比對，我決定後再做。

你會被問：缺的規格（沒有規格時 agent 會先用範本幫你寫）、比對後的編號決策清單，每項都有建議的預設值；上限、逾時這類數字只會問，不會幫你決定。範例畫面如果只在 Figma 或圖片裡，先走 A。

補畫面、補需求

做完之後常會發現少了畫面，或需求改了。直接說：

/design-aidlc 幫我補齊 <demo 名稱> 缺的狀態（錯誤、載入中、空狀態）。
/design-aidlc 找出 <demo 名稱> 裡沒有去處的按鈕和選單，補上需要的畫面。
/design-aidlc 需求有改：<改了什麼>。請更新 <demo 名稱> 的畫面和說明 md。
agent 自己補的畫面、動作、狀態，說明 md 那一列開頭會標 [AI 推測]。你看過、改過或確認沒問題後，把標記拿掉。

在專案裡開始

兩個專案（omni-family、omni-SMB）設定相同：平台有 app、win、mac、extension、desktop，語言 en 與 zh-TW，使用 TLDS。步驟也一樣，只是換路徑。

專案資料夾
omni-family~/Documents/HIE/projects/omni-family
omni-SMB~/Documents/HIE/projects/omni-SMB
  1. 開啟專案在 Claude 裡選該專案資料夾；或在 prompt 裡直接寫資料夾路徑，agent 會自己找。
  2. 說你要做什麼用上面 A、B、C 其中一種開頭，把路徑換成你的專案。 
    /design-aidlc 在 ~/Documents/HIE/projects/omni-family，把這個 Figma 連結做成設計 <Figma URL>，平台 app，放草稿。
    /design-aidlc 在 ~/Documents/HIE/projects/omni-SMB，使用者是<誰>，想要<做什麼>。請先列出需要的流程，我選了再做。
  3. 回答 agent 的問題平台、輸出區域（草稿、定稿協作、交付）沒說就會問。第一次選草稿會問你的草稿資料夾名稱，之後不再問。這兩個專案的文案風格層還沒指定，agent 可能會請你向專案負責人確認。
  4. 看成果、要求修改用中文說要改哪裡。agent 會自動補缺的狀態和沒去處的按鈕，並標 [AI 推測] 讓你檢查。
  5. 搬檔、檢查、交付PM 同意後 move draft-to-cowork，精修完 move cowork-to-delivery，再依序 finish、handoff（見上面「日常流程」）。

Slash 指令

在 Claude Code 裡輸入。

指令什麼時候用
/design-aidlc <需求>任何新增或修改畫面、流程、文案的請求
/design-aidlc finish做完、要 commit 或 review 前（由 finish-checker 檢查）

/design-aidlc-updatedesign-aidlc 有新版時，一次更新所有專案（見下一節）

更新連動

design-aidlc 本體更新後，專案裡的規則、連結要跟著更新。

一個指令搞定

/design-aidlc-update

也可以指定專案資料夾，不指定時會自動找 ~/Documents/HIE/projects/*，列出清單讓你確認後才跑。

它會依序做：

  1. pull design-aidlc 與 writers' handbook，在 design-aidlc 跑 npm ci（本機有未提交變更或無法 fast-forward 時會停下來問你）
  2. 對每個專案跑 update → link → doctor
  3. 用中文回報：哪些規則改了、哪些專案要處理、哪些檔案有變更
它不會 commit、也不會開 PR。專案裡 AGENTS.md 的規則區塊只由專案負責人更新：確認 diff 後 commit，開一個 PR。其他人 pull main 即可，不要各自 commit update 的結果。

手動步驟（不用 skill 時）

展開指令

① 更新本體

cd <安裝位置>/design-aidlc && git pull --ff-only && npm ci
cd <安裝位置>/trendlife-writers-handbook && git pull --ff-only

② 每個專案各跑一次

node <安裝位置>/design-aidlc/bin/design-aidlc.ts update --project <專案>
node <安裝位置>/design-aidlc/bin/design-aidlc.ts link   --project <專案>
node <安裝位置>/design-aidlc/bin/design-aidlc.ts doctor --project <專案>

注意：

  • update 說專案規則比你的新 → 先 pull design-aidlc 再跑；check 回報 project-outdated 也是同樣意思
  • 舊專案的 view/ 資料夾，update 會自動改名成 views/；兩個資料夾都是真的時不會合併，會提醒你處理
  • AGENTS.md、log.md、.gitignore 不要整檔 git restore，只用 git restore -p 丟掉 update 改的部分
  • 新版增加 subagent 一定要 link，doctor 的 links 要是 ok

TLDS 發新版時

展開步驟
  1. session 開啟時會跳 TLDS 提醒；check 會把落後的交付列為 tlds-behind
  2. 與工程確認升到 X.Y.Z
  3. 請 agent 跑 tlds sync（需 gh auth login）
  4. 請 agent 跑 ds-sync-reviewer，看過受影響畫面
  5. 單獨 commit：chore: TLDS X.Y.Z

其他指令

不用背語法，直接用中文跟 agent 說就好。每個指令下面有一句以 omni-family 專案為例的說法，只供參考；檔名與 slug 是示意，用時換成你自己的。灰框裡的語法是 agent 實際會跑的指令，需要時再複製。

doctor 對照

doctor 全部 ok 才算完成。出現下列狀況時：

顯示處理
sign-in: not signed in對 agent 說「幫我登入 TLDS Storybook」
rules block跑 update；若區塊比本機新，先 pull design-aidlc
links: missing or stale跑 link
TLDS reminder: not installed跑 link
TLDS: … behind與工程確認後跑 tlds sync
design map / demo shells跑 map
font smoothing跑 update
storybook-gaps.md 出現在 zone 裡只該有專案根目錄那一份，刪掉 zone 裡的
strings.generated.js 過期跑 strings
gh 未登入終端機跑 gh auth login
python3: not working跑 xcode-select --install

check 常見 finding

顯示處理
state-attribute用了自己發明的 data-when、data-state-only 等；改成標準的 data-state="<name>"，用 ?state=<name> 切換
strings-script有手寫的 *Strings.js；刪掉，改跑 strings 產生 strings.generated.js
platform-only某個 demo 只有一個平台有；補另一個平台，或在 demo 的 md 加一行 平台說明：… 寫明原因
project-outdated專案規則區塊比本機舊；跑 /design-aidlc-update
